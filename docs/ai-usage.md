# 생성형 AI 및 AI 코딩 도구 활용 내역

본 프로젝트는 생성형 AI를 결과물의 자동 완성 수단이 아니라, 팀원이 설계·검토 책임을 유지하는 **개발 보조 도구**로 활용했다. AI가 만든 문서와 코드는 그대로 채택하지 않고 요구사항, 설계 규칙, 테스트 결과를 기준으로 검증·수정했다.

## 1. 활용한 AI 도구

| 도구 | 활용 목적 |
|:---|:---|
| **Claude Code** | 요구사항·사용자 스토리 초안, 프론트엔드·백엔드 코드 작성 보조, 리팩터링, 코드 리뷰와 테스트 초안 생성 |
| **OpenAI GPT** *(운영 적용)* **· Anthropic Claude** | 서비스 탐색·기획 산출물 생성용 제품 AI 엔진. LLM Adapter로 추상화해 기능 단위로 제공자·모델을 지정하며, 현재 운영 환경에서는 전 기능을 OpenAI API로 호출 |
| **Figma · Playwright MCP** | 디자인 구조 확인과 디자인–코드 비교, 브라우저 동작 및 시각적 UI 검증 |
| **Context7 · Serena · GitHub MCP** | 공식 문서 조회, 심볼 단위 코드 탐색, 이슈·변경 이력 확인 |
| **claude-mem** | 세션의 작업 내용과 의사결정을 관측 기록으로 저장·검색하여 장기 작업의 맥락 유지 |
| **[`crew` 플러그인](https://github.com/gridi-ai/gridi-skills/tree/main/plugins/crew)** | 팀이 직접 개발한 직군별 스킬로 기획–설계–개발–QA–배포 흐름을 표준화 |

## 2. 활용 범위

- **기획·디자인**: 대화로 수집한 요구사항을 백로그와 사용자 스토리로 분해하고, 정책·화면 흐름·와이어프레임 초안을 작성했다. 이후 Figma의 실제 프레임, 컴포넌트, 아이콘과 비교하여 AI가 임의로 보완한 화면이나 정책을 제거했다.
- **설계**: 사용자 스토리를 기술 명세와 테스트 케이스로 구체화하고, OpenAPI 문서를 프론트엔드와 백엔드가 공유하는 계약으로 사용했다. 구현 전에 입력값, 권한, 정상·실패 흐름과 완료 조건을 문서로 고정했다.
- **개발·QA**: 확정된 설계와 API 계약을 입력으로 반복 코드, UI·백엔드 기능, 리팩터링 및 테스트 초안을 생성했다. 백엔드·프론트엔드는 독립 작업으로 병렬화하고, 결과는 단위 테스트와 Playwright E2E 및 브라우저 시각 검증으로 다시 합쳤다.
- **제품 기능**: 서비스 URL 분석과 신규 기획·정책 초안 생성에 LLM을 사용했다. 핵심 분석 로직과 프롬프트 설계는 영업비밀 보호를 위해 제출 저장소에서 추상화하거나 제외했다.

## 3. 하네스 엔지니어링 방식

단일 프롬프트의 품질에 의존하지 않고, AI가 일관된 절차와 근거를 따라 작업하도록 **맥락·역할·도구·검증 규칙을 개발 환경에 코드화**했다.

- **맥락 하네스**: 프로젝트 규칙 파일에 아키텍처, 네이밍, 기술 스택과 금지 사항을 명시하고, claude-mem으로 이전 세션의 결정과 변경 이유를 다음 작업에 주입했다.
- **워크플로우 하네스**: 자체 [`crew`](https://github.com/gridi-ai/gridi-skills/tree/main/plugins/crew) 플러그인이 `백로그 → 사용자 스토리·와이어프레임 → 기술 명세·테스트 케이스 → 디자인·API 명세·백엔드 테스트 → 구현 → E2E·QA → CI` 순서를 관리한다. PO·기획·디자인·FE·BE·QA·DevOps 역할을 분리하고, 의존성이 없는 작업만 병렬 실행했다.
- **산출물 하네스**: 사용자 스토리, 기술 명세, 테스트 케이스, 디자인 명세와 OpenAPI를 파일로 남겨 다음 에이전트의 입력으로 사용했다. 따라서 구현 근거와 요구사항 변경 이력을 사람이 추적할 수 있다.
- **도구·가드레일 하네스**: Figma·GitHub·Playwright·문서 조회 MCP를 작업 도구로 연결하고, 훅과 자동 명령으로 포맷·린트·타입 검사·테스트·빌드를 수행했다. 확률적인 생성은 AI가 담당하되 합격 여부는 재현 가능한 검사 결과로 판단했다.
- **사람의 검토 지점**: 요구사항과 설계 확정, 최종 기능 검수처럼 제품 판단이 필요한 단계는 팀이 승인했다. AI는 근거가 없는 정책을 결정하거나 검증 실패를 임의로 무시할 수 없도록 운영했다.

## 4. AI 생성 코드의 검증·수정 방식

1. **요구사항·설계 대조**: 기능 요구사항, Figma 디자인, OpenAPI 계약과 일치하는지 사람이 검토했다. 근거 없이 생성된 화면·정책·데이터 구조는 채택하지 않았다.
2. **변경 리뷰**: Git diff로 불필요한 변경, 기존 기능 삭제, 중복 구현, 보안 정보 포함 여부를 확인하고 변경 범위를 최소화했다.
3. **자동 검증**: 타입 검사, 린트, 포맷, 단위·통합 테스트와 빌드를 실행했다. 실패 로그를 기준으로 원인을 수정하고 같은 검사를 다시 통과할 때까지 반복했다.
4. **동작·시각 검증**: 주요 사용자 흐름은 Playwright와 실제 브라우저에서 재현했다. UI는 Figma 원본과 비교해 배치, 상태 변화, 반응형 동작과 아이콘을 수정했다.
5. **최종 승인**: 인증·권한·결제·데이터 변경처럼 영향이 큰 로직은 입력값, 예외 및 실패 경로까지 사람이 검토했다. 확인할 수 없거나 요구사항과 충돌하는 생성 결과는 제거하거나 다시 작성했다.

AI는 구현 속도와 탐색 범위를 넓히는 역할을 담당했으며, 최종 산출물의 정확성·안전성·일관성에 대한 책임은 팀이 맡았다. 생성과 검증을 분리하고 검증은 코드 리뷰와 결정론적 도구를 중심으로 수행했다.
